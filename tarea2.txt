Repuestos Vargas es una página web de venta y consulta de repuestos para electrodomésticos.

Está desarrollada utilizando Laravel, PHP, Blade, JavaScript y Tailwind CSS.

Actualmente tenemos dos versiones funcionales de la página de inicio.

- `resources/views/extras/home.blade.php`
- `resources/views/extras/layout.blade.php`

**Versión B — Rediseñada**

`http://127.0.0.1:8000/prueba-redisenado`

Archivos:

- `resources/views/extras/home-redisenado.blade.php`
- `resources/views/extras/layout-redisenado.blade.php`

Ambas vistas ya funcionan correctamente.

Se verificaron las rutas, controladores, renderización de Blade y respuestas HTTP 200.

## 2. ARQUITECTURA ACTUAL

El proyecto utiliza el controlador:

`app/Http/Controllers/CategoryController.php`

Actualmente:

- `index()` devuelve la vista original.

- Ambos reutilizan un método privado llamado `homeView()`.
- `homeView()` obtiene las categorías mediante `ProductCategory::all()`.
- Ambas vistas reciben la variable `$categories`.

Las rutas registradas incluyen:

- `/` → `CategoryController@index`
- `/prueba-redisenado` → `CategoryController@redisenado`
- `products.home`
- `products.byCategory`
- `extras.home`
- `extras.home-redisenado`

**No elimines ni sustituyas la lógica funcional del controlador.**

No lo recrees si no es necesario.

## 3. OBJETIVO GENERAL

Implementar PostHog para realizar un experimento A/B entre las dos versiones de Repuestos Vargas.

La distribución deseada es:

- Variante A: `control` — Página original.
- Variante B: `test` — Página rediseñada.
- Distribución: 50% / 50%.

La asignación de variantes debe realizarse mediante las feature flags de PostHog.

Cada visitante debe conservar su variante durante el experimento.

El objetivo es comparar cómo los cambios de diseño afectan la navegación y las interacciones de los usuarios.

## 8. TAREA 4 — CREAR LOS EVENTOS PERSONALIZADOS

Necesitamos registrar cuatro métricas.

La instrumentación debe funcionar en ambas versiones de Repuestos Vargas.

Puedes centralizarla en:

`resources/js/analytics.js`

Si el archivo ya existe, revísalo y modifícalo sin duplicar la inicialización.

Utiliza JavaScript y los eventos reales de los elementos HTML.

### MÉTRICA PRINCIPAL 1

**Nombre:** Tasa de clics hacia productos y categorías desde el navbar.

Evento:

`header_navigation_click`

El evento debe registrarse cuando el visitante hace clic en:

- Productos del navbar.
- Categorías del navbar.
- Enlaces equivalentes del menú móvil.

Propiedades mínimas:

- `destination`
- `navigation_type`
- `ab_variant`

Queremos distinguir las acciones que provienen del navbar de las que provienen de otros elementos de la página.

No contabilices los clics en tarjetas de categorías como si fueran clics del navbar.

El análisis debe permitir obtener la proporción de usuarios expuestos que realizaron al menos un clic relevante.

### MÉTRICA PRINCIPAL 2

**Nombre:** Clics en botones de contacto.

Evento:

`contact_click`

Registrar las interacciones con los enlaces existentes de:

- WhatsApp.
- Llamadas telefónicas.

Propiedades mínimas:

- `method`
- `ab_variant`
- `location`, si es útil para distinguir navbar, footer u otras ubicaciones.

Comprueba primero si realmente existen enlaces funcionales para WhatsApp y teléfono.

Si alguno no existe, repórtalo. No inventes un botón ni modifiques el diseño.

Si actualmente el teléfono aparece solamente como texto, no lo registres como un clic.

El evento representa la intención de contacto, no la confirmación de una conversación o llamada completada.

### MÉTRICA SECUNDARIA 1

**Nombre:** Búsquedas realizadas por sesión.

Evento:

`search_performed`

Identifica cómo funciona actualmente el buscador.

Puede ser:

- Formulario tradicional.
- Búsqueda AJAX.
- Buscador en tiempo real.

Instrumenta el comportamiento real, sin alterar sus funcionalidades.

Registra cada búsqueda efectivamente ejecutada.

Propiedades recomendadas:

- `ab_variant`
- `search_location`
- Identificador de sesión, si es necesario.

La fórmula requerida es:

`Total de búsquedas / Total de sesiones`

No confundas búsquedas por usuario con búsquedas por sesión.

Deja documentado cómo obtener el denominador correcto en PostHog.

Si no existe un buscador funcional, indícalo explícitamente y no inventes uno.

### MÉTRICA SECUNDARIA 2

**Nombre:** Tiempo hasta el primer clic en un producto.

Evento:

`product_first_click`

Debe registrar el tiempo desde el comienzo del recorrido evaluado hasta el primer clic del usuario en una ficha individual de producto.

Propiedad numérica obligatoria:

`elapsed_seconds`

Requisitos:

- Registrar el tiempo en segundos.
- Conservar el tiempo inicial al navegar entre páginas.
- Registrar únicamente el primer clic relevante de cada sesión.
- No contar el enlace general de Productos del navbar como un clic en una ficha.
- Evitar registros duplicados.
- Utilizar una definición coherente del comienzo de la medición en ambas variantes.
- Documentar qué ocurre con usuarios que no llegan a hacer clic en un producto.

El resultado debe permitir comparar el tiempo promedio entre las variantes A y B.
